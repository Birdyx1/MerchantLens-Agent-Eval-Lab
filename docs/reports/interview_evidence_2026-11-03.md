# 面试与简历证据（2026-11-03）

> 只写有真实证据支撑的内容。不能声称的部分明确列在最后一节。

## 一句话介绍

一个面向商家经营分析的 ReAct Agent 评测项目：用 Trace 记录轨迹，用代码裁判 + LLM 裁判评测，覆盖 NL2SQL、分层归因、对抗输入与安全门禁，并把异常数据回流成新评测任务。

## 可讲的点（附证据）

### 1. 评测体系
- 四类评测集合 + 密封 Holdout（哈希锁定，保证不被污染）；
- 题型覆盖 `store_net`、`store_net_sum`、`nl2sql`、`attribution`；
- 389 个测试保护，覆盖契约、裁判、门禁与复现。

### 2. NL2SQL 与归因评测
- `run_sql` 只读执行（SQLite `mode=ro`），按前缀分类拒绝写/DDL，返回结构化结果集；
- 结果集评测：列名/顺序/容差对齐，支持「取最后一条未截断结果」；
- 分层归因题：先查维度最高项、再下钻子维度，评测同时看「关键事实」与「查询证据链」；
- 4 道归因题真实运行 4/4 通过。

### 3. 对抗与安全门禁
- 8.1a 歧义/脏输入：硬约束裁判（Trace 有效、禁止工具、不声称执行）；
- 8.2 提示注入：4/4 通过，修复了「长 SQL 截断」和「反复验证耗尽步数」两个真实问题；
- 8.3 危险动作：4/4 通过；
- 8.4 安全一票否决：12 条汇总，修复 2 条违规后 **PASS**，并接入报告顶部。

### 4. 数据飞轮
- 异常识别：147 Trial 中识别 24 个异常（5 类规则）；
- 脱敏去重：24 → 14 候选，掩码密钥/手机号/邮箱，标注来源；
- 标注工作台：候选唯一、不可覆盖、状态机 `pending → one_label → agreed/disputed`；
- 入库门禁：只有 `agreed` 且判为真 badcase 才能转正式 Task；
- 修复回测与派生回归：`fixed/not_fixed`，badcase 可派生成 `regression_*`。

### 5. 工程实践
- 真实发现并修复的问题：浮点容差自相矛盾、大小写列名、SQL 截断、max_steps 耗尽、marker 过宽误判；
- 复现清单：8 个数据文件哈希校验通过；
- 标准报告：安全结论置顶，缺失证据写「未提供」而不是默认通过。

## 面试可能被问的问题

**Q：你的评测怎么防止过拟合？**
A：四集合物理隔离，密封 Holdout 用哈希锁定，只用于最终验收；调参只在前三个集合。

**Q：为什么安全要一票否决？**
A：通过率再高，一条越权/注入成功就说明不能发版；门禁把安全结论放在报告顶部，优先于通过率。

**Q：归因题怎么评？**
A：两条判据——`facts_present` 检查最终结论的关键事实，`query_evidence_present` 检查 SQL 是否真的查到对应维度，防止「猜对结论没有证据」。

**Q：你的局限是什么？**
A：样本小（对抗各 4 条）、单次运行、语义复核多是 LLM 裁判而非人工；数据飞轮的 14 条候选还没真人标注，所以没有真实入库。

## 不能声称的（红线）

- 不能说「线上生产环境安全通过」——样本是合成的；
- 不能说「标注一致性达到 X」——4 题、0 分歧，不能算稳定性；
- 不能说「数据飞轮已闭环」——候选还没标注、没入库、没回测；
- 不能把 LLM 裁判的结果说成人工复核；
- 不能说「UI 是正式产品」——它是原型。
