## 课时定位

汇总前序课时成果，形成第一份可展示的小规模评测报告：任务集、批量执行、轨迹、规则评分、失败分类，以及同一任务集上两个版本或配置的初步比较。报告记录运行配置、数据范围与证据路径，并说明小样本与规则评分的局限；阶段 10 再完善为标准报告。

## 方法论与证据门槛

首版报告必须形成“固定 Task → 多次 Trial → Trace → Code 规则评分 → 四类指标 → 失败归类 → 同题双配置比较”的闭环。两个批次须用同一集合、相同 Task 文件哈希和相同重复次数；否则分数变化可能来自题目变化。报告中的差值只是描述性结果，小样本不能直接声称显著提升。安全状态 `unknown` 不等于安全通过。

本课将 [Trial 到真实 LangGraph/MCP 的适配器](../../../src/merchant_agent/evaluation/live_invoke.py)接通：每次新建 MCP 会话和图，绑定该 Trial 的 SQLite、Trace 与 thread ID。测试模型必须实际调用 MCP SQL 并根据工具返回作答，完整链路经 [Code Evaluator](../../../src/merchant_agent/evaluation/code_evaluator.py)和指标计算通过。这个测试证明接线可用，**不是 DeepSeek 正式成绩**。

[双批次报告生成器](../../../src/merchant_agent/evaluation/report.py)要求两个完整批次与一致任务清单，拒绝缺少评分的 Trial；输出版本表、通过率差值、候选版失败判据、安全门禁和证据 Trial ID。根因分类目前以失败判据和 Trial 状态为主，复杂原因还需人工审阅 Trace。

## 实践任务与验收标准

教师已完成代码、本地端到端测试和同一 Regression 四题上的两版提示词真实运行：每版 8 个 Trial，均保留 Trace、规则与轨迹评分，结果均 8/8，候选 token 成本更高。此为单模型、小样本的同题双配置比较，仍需更多业务题、Judge 校准和安全证据，不能写成稳定生产提升。

## 面试考点与踩坑

问：为什么不能拿本地测试模型的满分写简历？答：它按固定测试逻辑调用工具，只验证流水线，不测真实基座能力。问：为什么要同题同次数？答：控制样本与重复设计，版本差值才有可比性。问：规则评分报告的边界？答：只覆盖当前固定 Rubric，不涵盖开放质量与全部安全行为。
