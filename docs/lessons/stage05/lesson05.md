## 方法论

批量评测是一个预先固定的实验：选定**一个集合、一组 Task 快照、模型版本、Harness 版本和每题重复次数**，再按同一规则运行、评分、聚合。不能在看见中途分数后增删题目或只补跑失败题。评测输入的 Task 文件名、ID 与 SHA-256 写入批次清单，运行前复核哈希，防止中途换题。Anthropic 的 Agent eval 方案将任务、试验和评分器分开；本项目的批次清单和落盘格式是工程设计。[Anthropic Agent Evals](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

本课采用**顺序执行**：每题每轮调用一次 5.1 Trial，随后用 5.2 规则评分、5.3 四类指标；全部完成后调用 5.4 的按题不确定性统计。这样先确保环境与证据边界清楚，后续再加有上限的并发。中途失败时批次标记 `failed`，已有 Trial 与未完成评分项仍保留，不能生成看似完整的成功率。

## 实践目标、输入输出

教师实现 [run_batch](../../../src/merchant_agent/evaluation/batch.py)。输入：项目根目录、单个正式集合、预设重复次数、模型/Harness 版本、每次运行的 `invoke_factory` 与可选超时。输出：`runs/batches/<batch_id>/batch.json`，包含冻结 Task 清单、逐 Trial 状态/评分/指标、聚合与区间。写盘使用同目录临时文件替换，避免中断留下半截 JSON。

`invoke_factory` 必须为每次 Trial 提供适配器；真实 DeepSeek/MCP 连接、模型会话是否重建由后续接线课验收。当前四集合没有正式样本，因此本课只能验证编排与故障保留，不能报告真实批量分数。

## 验收标准

- 空集合拒绝执行；每题恰好运行预设次数；Task 快照中途变化则停止。
- 每条 Trial 完成后及时保存；评分器失败时批次为 `failed`，已产生 Trial 不消失。
- 只有全部完成才生成聚合和不确定性结果；批次文件权限为 `600`。

## 面试考点与踩坑

问：为何先冻结任务清单？答：看分数再换题会引入选择偏差。问：批次失败时为何保留部分记录？答：用于定位模型、工具或评分器故障，且不能让失败样本从分母中悄悄消失。问：顺序执行是否够工业级？答：这是正确性基线；并发必须额外处理资源隔离、限流、重试和确定性汇总。问：能否用模拟评分宣称模型能力？答：不能，模拟测试只证明流水线行为。
