## 方法论

端到端评测同时问两个问题：**结果对吗**，**结果是按正确行动链得到的吗**。现有 Code Evaluator 已核对 Oracle 金额、必要工具和工具结果；本课再验证一次真实 Trace 中是否出现“规划指定正确工具及参数 → 工具成功返回相同金额 → 模型最终结束”的顺序。若只看答案，模型猜中 12000 分也会被误判为成功；若只查任意工具 Span，先给答案再补取证也可能蒙混过关。

评测对象是单次 Trial 的可信 Trace，不直接把模型隐藏推理当证据。样本来自隔离的 Golden/Regression/Badcase/Negative 集，真值与过程要求在运行前冻结。本课使用本地构造任务与真实 MCP/LangGraph 运行证明代码有效，不构成正式集合成绩。确定性证据用 Code Evaluator；开放性合理性仍交给固定 Rubric 的 Judge 和人工校准。关键 Trace 缺失时不得通过；安全负样例的违规由安全门禁一票否决，不能被本课成功率抵消。

这里的顺序判定依赖项目 JSONL 同步追加语义，是项目工程约定，并非 OpenTelemetry 标准字段。多进程异步写入时需用事件序号或因果链接替代文件行序。本课暂不声称证明模型在语义上真正使用了工具结果；可观测证据只支持“正确的调用和返回发生在最终决策前”。

## 实践任务与验收

教师实现[轨迹评测器](../../../src/merchant_agent/evaluation/trajectory_evaluator.py)。输入 Trial、冻结 Task 与项目目录；先复用快照哈希、Schema、Trace 关联及结果判定，再输出 `result_passed`、`trajectory_passed`、逐项检查和失败模式。必须在真实本地试验中通过，并在答案与工具结果不变、仅打乱最终决策顺序时识别为“结果正确、轨迹失败”。成本与安全指标沿用阶段 5 指标模块。

## 面试考点与踩坑

- 问：答案正确为何仍不能通过？答：必要工具、参数、结果及先后顺序是任务契约的一部分，猜中没有可追溯证据。
- 问：Trace 顺序证明了模型真的依据工具结果推理吗？答：不能，只能证明可观察的因果顺序；复杂任务还需 Judge 核验证据链。
- 坑：从整条 Trace 随便找一个正确规划会误配后续工具；应看该工具前最近一次规划。
- 坑：不可用结果成功率覆盖安全违规，安全门禁独立执行。
