## 方法论

端到端失败可能来自模型输出、解析器、路由器、预算或工具。组件评测先固定模型文本和 Agent 状态，再调用真实规划解析器与路由函数，观察它们是否给出预设动作。失败分为输出不符合契约的 `model_contract`、合法输出选错工具或参数的 `model_decision`、决策符合期望但路由不符的 `harness_route`。这些是定位线索，实际根因仍需结合提示词和接口复核。阿里 PawBench 的 Model × Harness 思路与字节 Data Agent 的分层评测都要求避免把两层问题混为一个成功率；本课的分类字段是项目约定。

样本应覆盖正确 SQL 选择、错误门店参数、无效 JSON、结束动作、步数预算与 token 预算。期望路由必须在运行前由人工或规则冻结，不能看见实际结果后改期望。若期望本身标错，所谓“Harness 失败”也会是假阳性，因此需要复核组件样本。

## 实践目标与验收

教师实现 [规划与路由组件评测器](../../../src/merchant_agent/evaluation/planning_component.py)：输入冻结模型输出、初始 State 和期望路由/工具参数；输出实际路由、是否通过和失败层。汇总时保留全部样本作分母，并分别报告模型契约与 Harness 路由失败数。专项测试包括正常 SQL 路由、预算阻断及故障注入后的归因。

四格实验的 32 条真实 Trial 首次规划输出已本地重放，四格各 8/8 与冻结 Task 的工具和参数期望一致；该数据全部来自净收入查询，不能推断跨任务规划能力。重放状态按项目默认预算和 Trace 用量重建，不等于持久化检查点快照。

## 面试考点与踩坑

问：为什么先冻结模型输出？答：重放同一输入可隔离路由器变化。问：模型输出非法 JSON 算 Harness bug 吗？答：本课归为模型契约失败，但提示词和接口契约也应复核。问：预算停止是失败吗？答：要看预设期望；超预算时阻断工具可能正是正确路由。问：为何需要人工复核期望？答：错误真值会造成错误归因。
