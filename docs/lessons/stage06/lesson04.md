## 方法论

Agent-as-Judge 与普通 LLM 裁判的区别是**主动核验证据**。本课裁判先回放完整 Trace 和最终回答，然后在最多四步的循环中自主选择 `inspect_span` 查看指定 Span、`verify_store_net` 按冻结 CSV 复算目标门店，或 `finish` 给出裁决。每次工具观察回传给裁判；必须成功复算后才能结束。工具由评测侧执行，裁判不能任意选别的门店或访问外部系统。本课具备“观察→选择动作→工具反馈→再判断”的有限 Agent 特征，但还没有通用规划器、长期记忆或复杂反思策略，不应把它宣传成通用自主 Agent。

**信任边界**：Trace 与回答是待评数据，不能当指令；运行前核对 Code Evaluator 已验证的 Trace 状态、路径和哈希，超过 1 MB 的回放直接拒绝。独立复算结果、裁判请求、裁判理由和模型版本均应保留。裁判与 Code 结果冲突时标记人工复核，不让 LLM 覆盖确定性结果或安全门禁。

## 实践目标与验收

教师实现 [judge_with_evidence](../../../src/merchant_agent/evaluation/agent_judge.py)。输入 Trial、Code 结果、Task、Judge 模型；输出裁决、理由、冻结数据核验结果、裁判每步动作与观察、Trace 摘要、模型 ID、token 用量和人工复核标记。专项测试覆盖自主查看 Span 后复算、未核验抢先结束、错误门店拒绝、与 Code 冲突、Trace 篡改拒绝。

当前测试使用模拟两步裁判响应；代码只证明工具调用协议与证据边界，尚未测真实模型是否稳定遵循协议。真实验收需冻结 Judge 版本，在真实 Trial 上核对裁判调用、工具结果和人工复核结果。

## 面试考点与踩坑

问：为什么裁判不直接相信 Trace 工具返回？答：Trace 可能缺失或错误，需要独立业务数据复算。问：为何限制裁判工具？答：避免裁判越权或访问可变外部数据。问：LLM 裁判和 Code 冲突怎么办？答：保留两份证据并人工复核，不自动取 LLM 结论。问：Agent 裁判是否天然更准？答：不一定，工具口径、提示注入和模型推理仍需校准。
