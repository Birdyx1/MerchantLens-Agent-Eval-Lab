## 方法论

成对比较让裁判在同一道 Task 的两个回答中选表达更清楚者，适合相对偏好分析；它不替代 6.1 的绝对分，也不覆盖 Code Evaluator 的金额和轨迹判据。两条回答必须来自**不同 Trial、相同 Task 文件哈希**。裁判只看固定清晰度 Rubric 和回答文本，不看版本名称，减少品牌或配置先验影响。

LLM 可能偏爱左侧、较长回答或先出现的答案。因此同一对回答交换位置评两次：若第一次选左、交换后选右，对应同一真实回答，才给出稳定胜者；若两次都选左，说明可能存在位置偏差，输出 `unstable`。两次均平局才记稳定平局。该设计是本项目的偏差诊断规则；一次交换无法消除所有裁判偏差，还需后续人工校准。[Anthropic Agent Evals](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

## 实践目标与验收

教师实现 [compare_answers](../../../src/merchant_agent/evaluation/pairwise_judge.py)：输入同题双 Trial、固定 Rubric、Judge 模型；输出两次原始选择及理由、顺序归一后的胜者、稳定性、Rubric 哈希、模型 ID 和两次 token 总量。Judge 输出必须是严格 JSON `{winner, reason}`；两次模型版本不一致则拒绝比较。专项测试覆盖稳定胜者、位置偏差、稳定平局与题目快照不一致。

单元测试使用模拟裁判响应。[真实试点](../../reports/pairwise_judge_challenges_2026-11-03.md)另对三对已双标的人工构造回答各交换顺序评一次，三对均稳定选中人工参考分较高者；首次非 JSON 输出失败保留，启用官方 JSON 模式后六次调用通过。三对数量很小且不是 Agent Trial，不能宣称位置偏差已消除或得出生产胜率。

## 面试考点与踩坑

问：为什么要交换顺序？答：检测位置偏好。问：`unstable` 如何处理？答：不强行归胜负，进入人工复核或多裁判流程。问：两个回答来自不同 Task 能否比较？答：不能，难度和上下文不同。问：成对比较胜率能否替代绝对正确率？答：不能，两个答案都可能错误。
