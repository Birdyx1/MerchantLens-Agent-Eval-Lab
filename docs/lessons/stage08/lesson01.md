## 方法论

本课评测两类输入。**歧义输入**缺少门店 ID 等决定性条件，期望 Agent 先澄清，不能猜 ID 后查询。**脏输入**含空值、畸形 ID 或格式噪声，期望按业务契约拒绝或要求修正，不能把无效参数送入工具。每个用例预先冻结类别、可见用户请求、期望行为和禁止调用的工具；期望行为留在评测侧，不传给模型。

优先用 Code Evaluator 检查禁止工具调用、Trace 有效性和是否有回复。但“回复真的在澄清吗”属于语义判断，非空字符串不能证明，因此硬约束通过后仍标记 `pending_review`，后续交给固定 Rubric 的 Judge 和人工抽样校准。安全违规不能由结果正确率抵消。对抗集必须物理放在 Negative Set，与 Golden/Regression/Badcase 分开；本课样本契约是项目自定义，尚未接到正式 Task Schema、双人仲裁和批量运行器。

风险：如果评测时模型看到用例标签、禁止工具清单或期望行为，会产生 Eval Awareness 污染；这些字段只供评测控制面使用。要同时记录正确拒绝率、误拒率及无效工具调用率，避免“一律拒绝”刷高安全分。

## 面试考点与踩坑

- 问：模型回复“请补充信息”就算通过吗？答：只能通过硬约束预检；是否具体、恰当地澄清须按 Rubric 判断。
- 问：歧义题为什么要指定禁止工具？答：在缺失关键参数时，调用依赖该参数的工具就是可观察的过程违规。
- 坑：拒绝所有输入可能提高负样例分数，却严重损害正常任务，须同时测误拒率。
- 坑：对抗样本若进入 few-shot 或提示词，会污染测试。
