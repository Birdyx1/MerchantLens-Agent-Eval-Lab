## 方法论 1：一致性先检查“同题同环境”

两份标签只有在标注者 ID 不同、Task 内容摘要相同、订单快照摘要相同的前提下才能比较。若 A 标的是旧订单、B 标的是新订单，分歧不能解释为人对 Rubric 的理解不同。美团把“人人一致”作为评测量具可信度的条件；Anthropic 把标注者间一致性和分歧复核用于人工评测。[美团白皮书](https://tech.meituan.com/2026/09/10/Agent-Evaluation-White-Paper-01.html) · [Anthropic Agent Evals](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

本课比较三个结构化字段：**是否可解、净收入金额、门店 ID**。证据说明保留给仲裁审阅，但文字措辞不同不算标签分歧。整题精确一致率是三个字段都相同时的比例；逐字段一致率用于定位到底是哪条判据模糊。两人都认为不可解时，金额和门店字段是“不适用”，不能把两个 `null` 算作金额一致来抬高指标。

## 方法论 2：一致率和 Kappa 各回答什么

原始一致率 = 判断相同的 Task 数 ÷ 已配对 Task 数，直观但容易受类别分布影响。例如几乎所有题都“可解”，两人一直选可解，原始一致率会很高。可解性作为二分类标签时，本项目同时支持 Cohen's κ：`κ = (观察一致率 − 随机期望一致率) / (1 − 随机期望一致率)`。[scikit-learn 的 Cohen Kappa 说明](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.cohen_kappa_score.html)

κ 只在**至少两道题、同一对标注者、分母非零**时计算；否则输出空值，不伪造一个“可靠”的系数。即便数学上可计算，两道题的 κ 仍非常不稳定；真实报告必须给出样本数、类别分布、逐项分歧和人工复核记录。金额是精确数值，本课报告精确一致率，不套用二分类 κ。

## 方法论 3：分歧必须显式仲裁

两人一致时可以形成 `consensus` 记录；两人分歧时，要求**第三个不同 ID 的仲裁者**写最终判断和理由，不能自动取平均金额，也不能默认相信先提交者。仲裁记录绑定两份原始标签的 SHA-256；原始记录改动、Task 或环境变化都会使它失效。

盲标摘要绑定用户问题、环境与 Rubric 版本，**不包含原有 Oracle 和流程状态**：这样发现原 Oracle 写错后，可以按仲裁结果修正它，再把 `label_status` 改为 `adjudicated`，而无需让两人重标完全相同的问题。Golden、Regression、Negative 的入库器现在还会检查仲裁真值是否与最终 Task Oracle 一致；只改 `label_status` 不能通过门禁。

两人一致仍可能一起算错。对当前可复算的订单任务，入库器还从冻结 CSV 独立计算 `已支付金额－退款金额`，要求它与仲裁真值、Task Oracle 一致。这个确定性参考解只适用于当前业务口径；开放任务需换成相应的证据核验方法，不能把无法复算的答案伪装成代码真值。

## 实践产物与数据流

- [一致性与仲裁代码](../../../src/merchant_agent/evaluation/agreement.py)：读取并校验两份原始标注，输出逐字段分歧、批量一致率与可解性 κ；生成共识或第三方仲裁记录。
- [仲裁 Schema](../../../schemas/adjudication.schema.json)：固定来源记录摘要、最终判断、理由与时间；记录存于 Git 忽略的 `runs/adjudications/`，权限为 `600`。
- [Task 摘要](../../../src/merchant_agent/evaluation/task.py)排除 Oracle 和 `label_status`；[业务参考解](../../../src/merchant_agent/evaluation/reference.py)从冻结 CSV 独立复算；[四集合入库器](../../../src/merchant_agent/evaluation/sets.py)核对原始记录、仲裁记录、Task Oracle 与业务参考解。

流程为：两份独立标注 → 同题同环境检查 → 分歧报告 → 共识／第三方仲裁 → 核对最终 Oracle 与冻结数据参考解 → 受控入库。**测试使用模拟 reviewer ID 和模拟标签，没有真实人工一致性结果，也没有将样本放进 Golden。**

## 验收、踩坑与面试考点

测试覆盖一致时自动形成共识、金额分歧必须第三方仲裁、原始记录被改动后失效、错误 Oracle 或与冻结数据不符的共识阻止入库、仅把状态改成“已仲裁”不能入库、不可解样本的金额一致率为不适用，以及参考解计算。测试结果见本课提交记录。

面试要解释：为何高一致率仍可能不可靠？可能类别极不平衡、样本太少，或两人看过同一参考答案。为何保留原始分歧？它可能揭示 Task 歧义、业务口径冲突或 Rubric 不清楚。当前 `reviewer_id` 不具备身份认证，原始记录只在本机 `runs/`，生产工作台还需账号隔离、不可篡改审计与持久化归档。
