## 知识点：评测分数为什么会被污染

若同一题进了 few-shot、调参样本或公开回归集，再拿它声称“未见题泛化”，分数就会偏乐观。Holdout 是**预留的独立样本池**：在固定开发周期内不用于提示词、模型或 Harness 调参，只在约定的版本验收点打开。美团的评测量具与数据闭环、Anthropic 的任务集与 grader 设计都强调样本和评价过程的可信性；本课的目录、哈希及流量标记是项目工程取舍，不是四家博客统一规定的字段。[美团白皮书](https://tech.meituan.com/2026/09/10/Agent-Evaluation-White-Paper-01.html) · [Anthropic Agent Evals](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

**与 Golden 的差别**：Golden 可以供版本横比、误差分析和修复；Holdout 在一个周期内少看、少用，衡量这些修改能否迁移到未参与决策的题。它不属于 Golden、Regression、Badcase、Negative 四集合，放在 Git 忽略的 `holdout/tasks/`。本机文件权限为 `600`，目录尝试以 `700` 创建；真实团队还需要独立权限、访问审计、加密存储与冻结版本。

## 实践目标与数据流

教师实现 [HoldoutStore 与调度边界](../../../src/merchant_agent/evaluation/holdout.py)：Task 必须先通过 Schema、冻结环境、Rubric、双标仲裁与业务参考解校验。Holdout 和四集合共用入库锁，拒绝同 ID；即使换 ID，也拒绝题型、Rubric、用户请求及环境快照完全相同的题面。反向从四集合入库时也查 Holdout。

运行器调用 `prepare_eval_dispatch` 得到两个分离的值：`agent_input` 仅含用户请求；`metadata` 留给评测控制面，含 `traffic_type=evaluation`、集合、Task ID 和 Run ID。**运行器后续必须把 metadata 写入运行记录或 Trace 外围索引，不得拼接到模型提示词。**此处还没有批量运行器，因此只能验收调度契约，不能声称端到端测试流量隔离已经完成。

`reject_eval_prompts_in_fewshot` 在组装示例前查已登记评测题的原始请求，精确命中就拒绝。它防止直接复制；不能识别同义改写、外部训练语料泄露或未登记草稿。上线需增加近重复审计、样本访问日志和训练数据来源核查。

## 验收与轮换规则

- 已验收：独立目录、入库证据门禁、跨集合 ID 与完全相同题面拦截、few-shot 精确命中拒绝、控制面标记不进入 `agent_input`。专项测试 4 个；全套 pytest 见提交记录。
- 待真实执行：由独立标注者建立 Holdout；记录冻结日期、版本、样本哈希和谁访问过；在预定验收点运行。当前没有真实 Holdout 样本，不能报告其分数。
- 轮换策略：每个评测周期先封存新题，再公布上一周期可用于分析的题；若题面被调参、提示词或公开报告引用，立即退役该题，下一次不能继续当未见题。退役与补题需要版本化清单和双人复核。自动轮换器尚未实现，留待报告/数据飞轮阶段接线。

## 面试考点与踩坑

问：为什么同一 Task 换个 ID 仍是污染？答：Agent 看到的题面与环境没变，换 ID 不会恢复独立性。问：测试流量标记放哪里？答：放调度/审计元数据，不能在 prompt 里写“这是评测”。问：Holdout 只靠 `.gitignore` 够吗？答：不够；它只避免常规 Git 提交，不限制本机读取，也不阻止题面被人工复制。问：重复题检测的边界？答：当前做结构化完全相同检测，近重复与语义改写尚无保证。
